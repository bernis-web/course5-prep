# 第 5 章　为什么我们这么强调"可复现"

> 这一章只讲**为什么**。本项目最贵的一次翻车不是算错了，而是**算对了却说不清这份结果是从哪份代码、哪份数据跑出来的**。

## 5.1 sha256 冻结：给每个文件发一张"身份证"

**sha256 是什么**：把文件内容塞进一个公式，吐出一串 64 位十六进制字符串。改一个空格，这串字符就完全变样；反过来，字符串一样内容就一样。它当"指纹"用，不当"加密"用。

**为什么每次跑完要记哈希**："这份 predictions 是哪次跑出来的"只能靠哈希回答，不能靠文件名回答。哈希写进 `sha256.tsv` 就是发身份证——别人自己算一遍，和表里对上才算认领成功。

### 我们真踩过的 6 个坑

**坑① 同一个文件名，不等于同一个文件。** 平台上的 `/Files/ResultData/Notebook/ortholog_pca_dcs_v3_fixkey.txt`（17,382 B / 421 行 / `json.loads` 在第 167 行 / sha256 `514d9314…`）和本地的 `scripts/ortholog_pca_dcs_v3_fixkey.py`（16,463 B / 383 行 / `csv.DictReader` 在第 123 行 / sha256 `f9683cf9…`）**是两个不同的文件**。两者都有个 `freeze_mapping` 同名函数，但一个读 JSON、一个读 TSV。第一次在镜像里失败，就是把 TSV 喂给了读 JSON 那版，报 `JSONDecodeError: Expecting value: line 1 column 1 (char 0)`。光看名字你会以为"就是那个脚本"，一算 sha256 立刻知道不是。

**坑② 靠计划文档推断"原件"，推错。** 我们一度认定平台上的 `samap_v98_emb.txt` 是没打补丁的原件。下载回来一算：17,194 B / 422 行 / SHA `418ac586…`，里面本来就有 `EMB_SAVED` 和 `samap_joint_embedding.npy` 的保存代码。计划文档会过期，平台上的文件才是事实。

**坑③ 指标同名，算法不同版。** 旧草表那组 `80.9 / 38.3 / 40.5 / 22.4 / 11.9 / 79.5` 已作废：一是排除规则失效（`coarse_level=='unmapped'` 一个都没命中，74 个该排除的细胞留在分母里），二是**评分器不是统一那版**（v75c/v78b 容器输出，与冻结的 KNN/置换定义有实现差异）。所以光锁数据不够，产出分数的**代码**也得锁。

**坑④ 同一个 bug，两个版本号。** v98 的斑马鱼方向同源映射没取反（已修），冻结值是 19.61 / 27.55；修正后 FIXKEY 权威值是 17.95 / 26.75。人↔鼠两向两口径相同（86.18 / 73.69）。所以数字必须带版本名，裸数字等于没信息。

**坑⑤ 哈希相同，不代表内容对。** 平台那一页的 headless 截图被合成器缓存——连续三张截图 sha256 **完全相同**，而 DOM 已经更新。哈希只证明"两次拿到的东西一样"，不证明"这个东西对"。取证以 DOM 为准。

**坑⑥ 手写数字必错。** report-03 里六方向均值按印象写成 0.4988 / 0.4200 / 0.3922，实际是 0.4986 / 0.4611 / 0.3857（SAMap 0.0334）。所有表格数字必须从 `metrics.json` 用脚本生成。

## 5.2 环境记录：证明"在哪跑出来的"

**为什么存**：一个分数只在特定环境里成立。`environment.txt` 记三件事：**跑在哪个平台、什么包版本、什么镜像**。实测跑通的组合是 python 3.9 / numpy 1.23.5 / scipy 1.10.1 / pandas 1.5.3 / scikit-learn 1.6.1 / anndata 0.10.8 / scanpy 1.9.3 / h5py 3.8.0 / scvi-tools 1.1.6.post2 / torch 2.6.0+cu124。

**一个反直觉的结论**：本地 scipy 1.12.0 / pandas 2.3.3 / anndata 0.10.9 跟锁的版本**都不一样**，6 个冻结值仍 100% 复现。也就是说——**锁版本是为了"可复现"，不是为了"算得对"**。

**镜像要单独记**，因为平台镜像是"**基础镜像 + pip 包清单**"，跟 Dockerfile 是两套机制。构建成功的是 `g5-opca-container`（2026-10-30）。另纠正一个错判：文档里一度都写"平台镜像构建通道失败"，实际数了一遍，5 次尝试里有 1 次成功（`g5-canary-pinned`，2026-09-21 20:43，基于 `SATURN--22`），`system` 的 `centos-7`、`zhongliyuan` 的 `SATURN--22` 也成功了——**通道可用，失败集中在 SAMap/kBET 那种复杂依赖上**。"失败过"不等于"不能用"。

## 5.3 产物目录结构：每个文件各管一件事

以镜像内那次跑为例，产物目录是 `/work/user50719-8334/opca-full-20261031T115728Z/`：

| 文件/目录 | 管什么 | 为什么非它不可 |
| --- | --- | --- |
| `metrics.json` | 分数本体（accuracy、macro-F1、SE/CI） | 唯一"官方数字"来源，表格一律从这里生成 |
| `predictions/` | 逐细胞预测 | **唯一能换口径重算的东西**。18 份逐细胞预测独立重算，才有 union 口径的权威数字表 |
| `confusion/` | 混淆矩阵 | 别人能独立验的最小证据。跨门 macro-F1 改成 0.0235–0.0267，就是因为这个区间**能从混淆矩阵复现** |
| `manifest.json` | 这次跑用了哪些输入、参数、版本 | 回答"谁、用什么生成的"，含 `script_sha256` / `mapping_sha256` |
| `sha256.tsv` | 每个产物的哈希 | 防篡改、防同名混淆（见坑①） |
| `environment.txt` | 环境快照 | 回答"在哪跑出来的"（见 5.2） |

**为什么拆这么细**：`metrics.json` 只给结论，`predictions/` 和 `confusion/` 给"别人能不能自己算一遍"。只交前者等于只交答案，别人只能信你。

> 待确认：`manifest.json` 与 `environment.txt` 的具体字段清单，素材只记了"含哪些"，未逐字段列出。

## 5.4 为什么"能复现"比"分数高"更重要

**因为高分是别人的，能复现才是自己的。** 四个真实取舍：

1. **86.18% 再高，签字前也不能当结论。** 它的基础是 `config/heart-celltype-map-v1.tsv`（38 行、35 个 active、3 个 unmapped），`reviewer` 列**全是 pending**。这张表决定分母里装谁，按纪律要导师签字才能从 `needs-reviewer` 改成 `confirmed`。
2. **我们主动把数字改难看了。** 跨门 macro-F1 旧存值 0.0652–0.0802 **来源不明**（accuracy 与混淆矩阵完全一致，macro-F1 却差约 3 倍），换成可从混淆矩阵复现的 0.0235–0.0267。换完负结果更强：两个方法都低于多数类基线（0.0235 < 0.0274、0.0257 < 0.0360）。
3. **能复现才敢改结论。** SATURN 全列在 2026-11-08 被重算：根因是评测把**真值按源物种词表、预测按目标物种词表**查表（颠倒），两侧各丢一批细胞。修正后六向 0.3522 / 0.2566 / 0.1269 / 0.1640 / 0.3658 / 0.3563，一个方向都不赢。结论从"SATURN 首选"改成"scVI 首选"，**但理由是纠错，不是换口径**。见 `docs/reports/report-09-corrections-20261108.md`。
4. **最高形态是逐位复现。** 2026-10-31，任务 `2116497194053881858` 在 `g5-opca-container` 里跑通完整评估，**6 个冻结 coarse accuracy 逐位复现（6/6）**。日志里有 `script_sha256`、`mapping_sha256`、`ortholog pairs: hm=17611 fh=10398 fmm=9058`，最后 `DONE`。

一句话总结：**分数会被质疑，哈希和目录结构不会。**

# 第 6 章　组员最容易问的 10 个问题（FAQ）

## Q1　SATURN 是不是没用？

**一句话答**：不是没用，是它原来的分数被我们评测实现里的一个查表 bug 抬高了；修正后它明显落后，但那是"在这套数据上"的结论。

**详细说**：旧算法把真值按源物种词表查、预测按目标物种词表查，方向反了，导致真值侧查不到的被跳过、预测侧查不到的被判成不可映射，两侧都少了一批细胞。修正后鼠→斑马鱼 0.3658、斑马鱼→鼠 0.3563，两向都落后 scVI。但要分清：这是**我们的评测实现**有 bug，不是 SATURN 方法本身被证伪——换个数据集、换成留出评估，结论可能不同。它在批次混合那栏缺席，是重训会造出"同一方法的两个版本"这种假对照，不是没做。

## Q2　为什么我们的数字和别人论文里不一样？

**一句话答**：口径不同，一共六处，每一处都能让数字变。

**详细说**：① union 还是 truth-only（见 Q8）；② 分母不同，oPCA 1499–1528、scVI 1499–1528、SATURN 459–1309、SAMap 307–1368；③ 我们是 transductive / in-sample，不是留出评估；④ 规模差 300 倍，原文用完整图谱，我们每物种约 1,500 细胞；⑤ 只喂一对一同源基因（人鼠 15,869 / 人鱼 9,311 / 鼠鱼 8,160），原文用含 many-to-many 的全同源图；⑥ 同源来源不同，原文用 BLASTP 建图，我们用现成直系同源表。引用任何数，必须连口径一起说。

## Q3　oPCA 这么快，为什么不全都用它？

**一句话答**：门内它已经明显落后，跨门它和 scVI 一起塌，快不等于够用。

**详细说**：门内人→鱼时 scVI 是 oPCA 的 2.4 倍（0.4014 对 0.1654，FIXKEY 口径）。到跨门两者一起掉到 0.05 量级，没有实质差别。它的价值在"近缘、要快、要能解释"的场景，不在"跨得远还要准"。

## Q4　86.18% 这个数是怎么来的？为什么说它"依赖未签认的映射表"？

**一句话答**：它是人→鼠 coarse accuracy 的 FIXKEY 口径值，前提是一张没人签过字的细胞类型映射表。

**详细说**：这张表是 `config/heart-celltype-map-v1.tsv`，38 行、35 个 active、3 个 unmapped，`reviewer` 列**全是 pending**。它决定哪些细胞类型参与评估，也就是决定分母里装谁；分母一变，86.18% 就变。所以签字前只能标 `needs-reviewer`，不能当结论引用。

## Q5　什么叫"算得对"不等于"分得对"？

**一句话答**：accuracy 高只说明多数类猜中了，macro-F1 才看每个类有没有被分开。

**详细说**：跨门那次 accuracy 和混淆矩阵完全一致，但旧存值 macro-F1 比可复现值高约 3 倍（0.0652–0.0802 对 0.0235–0.0267）。换口径后两个方法都低于多数类基线（0.0235 < 0.0274、0.0257 < 0.0360）。反过来也有：三个方法 iLISI 只有 1.006–1.120（满值 3），看着像全失败，但同一份 scVI 潜空间上人→鼠 macro-F1 有 0.6683。

## Q6　跨门为什么效果这么差？是不是方法不行？

**一句话答**：不是方法不行，是"越远越靠潜空间"这个规律在跨门这一步断了。

**详细说**：门内人→鱼时 scVI 还是 oPCA 的 2.4 倍，到跨门两者一起塌到 0.05 量级，谁也没优势。所以这是我们这个规模下的负结果，不是判决书。三条限定语必须随数字出现：全部是 transductive、四个方法分母不同、"不推荐"不等于"方法差"。

## Q7　平台标"失败"的任务是真的失败吗？

**一句话答**：不是，至少有一次它其实跑成功了，只是最后一行命令报错。

**详细说**：任务 `2116497194053881858` 平台标失败，实际 6 个冻结 coarse accuracy 逐位复现（6/6）。原因是 `fixkey.sh` 最后一步 `cat $OPCA_OUT/metrics.json`，而脚本读的变量是 `OPCA_OUT_ROOT`，`cat` 找不到文件、退出码非 0，产物其实已经写好了。同类还有一次：`samap_v98_emb.txt` 报"上传失败"，文件早就在 `/Files/ResultData/Notebook/` 里。**别人说失败，要用独立证据复核。**

## Q8　为什么要同时报两个口径？只报公平口径不行吗？

**一句话答**：行，但你必须说清用的是哪个，否则别人对不上号。

**详细说**：两个口径是 truth-only（只按真实标签集平均，平台 scVI 脚本默认）和 union（真实∪预测一起平均，多预测的类记 F1=0）。实例：人→斑马鱼 coarse，truth-only 0.4516、union 0.4014，差 0.05 就够翻转结论。跨方法比较一律用 union，且从逐细胞预测独立重算。单独看 truth-only 不算错，错在把它和别的方法并列。

## Q9　老师七条意见我们到底怎么落的？

**一句话答**：一条一句，全落在报告和数字里了。

- **一、近缘/远缘/跨门分开说**：不给总分冠军，改成"场景→推荐谁"的选型表。
- **二、百分数要带稳定性**：每个分数配 ±bootstrap SE 与 95% CI（22 行全表在 `results/bootstrap-20261030/bootstrap.json`）。
- **三、结论和原文不一样要说清**：列了三条原因（规模差 300 倍、只喂 1:1 同源、同源来源不同），并自查出 SATURN 口径抬高。
- **四、实际消耗**：平台任务台账 + 本地白盒测量都出表了。
- **五、流程要有名字**：定为 XenoTransfer v1.0。
- **六、GitHub / DCS**：仓库在但推不上去（临时文件、凭据核查、LICENSE 未清）；DCS 可以发但没发。
- **七、新增实验与产物**：镜像构建成功 + 镜像内 6 个冻结值逐位复现，产物可复核。

## Q10　我想自己跑一遍，从哪开始？

**一句话答**：别从零搭，从已经跑通的那条路复制。

**详细说**：流程用 2026-10-05 跑通过的 `runsamap`（5 个输入：三份 h5ad + 脚本 + pylibs），不要用只声明 2 个输入的那版。镜像用 `g5-opca-container`，`container/entrypoint.sh` 现在导出 7 个变量，脚本读几个就得导几个。`import` 报错别猜，做二分测试（先 torch、再 anndata、最后 scvi），解压 pylibs 后先 `rm -rf ./pylibs_full/anndata ./pylibs_full/anndata-*.dist-info`。页面下拉恒"无数据"时用 `dcs task run` 投递绕开。跑完把 `predictions/`、`confusion/`、`manifest.json`、`sha256.tsv`、`environment.txt` 一起收走。
