## 一、我自己判断错了、后来更正的（最危险，因为结论会连带错）

这一类最值得看——**判断错了会导致整份材料跟着错**。

### 坑 1：看到 WDL 报 `RBRACE` 就以为「平台不支持 heredoc」

- **现象**：WDL 校验报错 `Expected one of: ... Previous tokens: [Token('RBRACE', '}')] at line 35, column 27`
- **我的错误判断**：平台 WDL 解析器不支持 command 块里的 heredoc（`<<'PATCH'`）
- **真实原因**：我用的是 `command { ... }` 花括号形式，而命令段里有 Python 字典字面量 `{"a": 1}`，**里面的 `}` 把 command 块提前闭合了**
- **正确做法**：WDL 命令段一律用 `command <<< ... >>>` 三尖括号形式。改用后校验立刻通过
- **教训**：报错 token 是 `RBRACE` 时，先数一数命令里有没有裸的 `}`，别急着怪平台
- **证据**：`docs/reports/batch-mixing-and-crossphylum-feasibility-20261019.md` §8.6

### 坑 2：把「上传失败」当成通道坏了，其实文件已经落盘

- **现象**：GenPilot 报 `samap_v98_emb.txt` 上传失败，第二次还明确说「请在数据管理的操作记录查看失败原因」
- **我的错误判断**：平台上传通道阻塞，这条路走不通，准备放弃
- **真实情况**：`samap_v98_emb.txt` 和 `opca_batch_metrics.txt` **已经都在 `/Files/ResultData/Notebook/` 里**了，只是延迟入库。我信了 GenPilot 的报错，没自己去列表核对
- **正确做法**：上传后**自己查一次文件列表**再下结论，不要只信返回消息
- **教训**：别人（包括 AI 助手）说「失败」，要用独立证据复核
- **证据**：同上 §8.6 第 1 条

### 坑 3：`samap_emb` 流程失败，我以为是 `cp` 命令没生效

- **现象**：任务跑完 16 分钟，产物只有一个 200 字节的 run.log，内容 `python3: can't open file './samap_script.py': [Errno 2] No such file or directory`
- **我的错误判断**：`cp ${script_txt} ./samap_script.py` 没生效，可能是 `set -u` 没配 `set -e` 导致错误被吞
- **真实原因**：那个流程**只声明了 2 个输入**（`script_txt` + `pylibs_tar`），三份 h5ad 从来没被 stage 进工作目录。就算 `cp` 成功了，脚本也会在读 `./human_saturn_input_s.h5ad` 时崩
- **正确做法**：用 2026-10-05 跑通过的 `runsamap` 流程（5 个输入：三份 h5ad + 脚本 + pylibs）
- **教训**：WDL 失败先检查**输入声明是否完整**，再看命令段
- **证据**：`docs/reports/batch-mixing-and-crossphylum-feasibility-20261019.md` §8.8

### 坑 4：把 `plan` 里残留的「待埋点原件」当成事实

- **现象**：我一直以为 `/Files` 上的 `samap_v98_emb.txt` 是没打补丁的原件，需要另外准备一个打了补丁的版本
- **真实情况**：把它下载回来一看（17,194 B / 422 行 / SHA `418ac586…`），**里面本来就有** `EMB_SAVED` 和 `samap_joint_embedding.npy` 的保存代码
- **正确做法**：把平台上的文件下回来核对 SHA 和内容，不要根据本地目录里的计划文档推断
- **教训**：计划文档会过期；**平台上的文件才是事实**
- **证据**：同上 §8.8

### 坑 5：以为「平台镜像构建通道失败」

- **现象**：多个文档里都写着「平台镜像构建通道失败」，我一直当既定事实
- **真实情况**：去镜像管理页数了一下，5 次尝试里**有 1 次成功**——`g5-canary-pinned`（2026-09-21 20:43，基于 SATURN--22）。另有 system 的 centos-7、zhongliyuan 的 SATURN--22 也是成功的
- **正确做法**：通道可用；失败集中在 SAMap/kBET 那种复杂依赖上
- **教训**：**「失败过」不等于「不能用」**，要数清楚成功率
- **证据**：`container/README.md` §7.4

### 坑 6：以为「本机没有 Docker」

- **现象**：容器化一直标为「本机无 Docker，无法构建」
- **真实情况**：`docker --version` 是 **29.8.2**，装了。真正的问题是 **WSL 一个发行版都没装**（`wsl -l -v` 报「没有已安装的分发」），Docker Desktop 的 Linux daemon 起不来
- **正确做法**：`wsl --install -d Ubuntu`（需重启）
- **教训**：诊断要往下追一层。「没有 X」往往其实是「X 装在，但依赖没配好」

### 坑 7：误判 scVI 首次失败「跑了 4.5 小时」

- **现象**：任务 `W202610170092924` 我看到页面显示已过 4.5 小时，就写进了文档
- **真实情况**：billing 只有 **566 秒（9.4 分钟）**，CPU 时间 29 秒。原因是我长时间没刷新页面，读的是**缓存的旧状态**
- **正确做法**：查任务详情接口或刷新页面取最新状态
- **教训**：**页面上的时间可能是缓存**，涉及「耗时/费用」的结论必须取自接口数据

### 坑 8：以为「torch 不存在」，其实是 anndata 冲突

- **现象**：`import scvi` 失败，我先怀疑镜像里没装 torch
- **真实情况**：二分测试（任务 `W202610180098593`）证明 **torch 2.6.0+cu124 在**。真正原因是 `pylibs_full` 里的旧 anndata 经 `PYTHONPATH` 抢在镜像自带 0.10.8 前面加载，而镜像里的 `mudata` 需要新版 anndata 的 `AlignedViewMixin`
- **正确做法**：解压 pylibs 后执行 `rm -rf ./pylibs_full/anndata ./pylibs_full/anndata-*.dist-info`
- **教训**：`import` 失败别猜，做**二分测试**（先只 import torch，再只 import anndata，最后 import scvi）
- **证据**：`docs/execution/20261019-handoff-full.md` §7.1

## 二、会烧钱或烧时间的坑

### 坑 9：Shell 变量不加引号 → 拷贝了整个根文件系统（¥0.58）

- **现象**：任务 IO 冲到 95 GB，费用 ¥0.58
- **根因**：写的是 `if [ -n $REC ]; then`。当 `$REC` 为空时，这行退化成 `[ -n ]`，bash 判定为**真**，于是执行了 `cp -r $REC/. ./result/` → 变成 `cp -r /. ./result/`，开始拷根目录
- **正确做法**：**所有变量引用一律加引号**
  ```bash
  [ -n "$REC" ]          # 不是 [ -n $REC ]
  cp -r "$OUT"/. ./result/   # 不是 cp -r $OUT/.
  ```
- **教训**：这是 bash 最经典的坑，且在这里真的花了钱
- **证据**：`docs/execution/20261019-handoff-full.md` §7.3

### 坑 10：`../result` 在容器里不可写

- **现象**：任务 1 秒内失败，`Container exited with status 1`
- **根因**：WDL 命令段写 `cp -r xxx ../result`
- **正确做法**：`mkdir -p ./result`，WDL 里声明 `File result = "./result"`
- **证据**：同上 §7.2

### 坑 11：输出目录名不匹配 → 产物收集不到

- **现象**：任务成功但产物目录是空的
- **根因**：脚本写的输出目录是 `opca-scvi-*`，而 WDL 的 glob 找的是 `opca-full-*`
- **正确做法**：用 `find` 收集，且**变量必须加引号**
  ```bash
  find . -name 'samap_joint_embedding.npy' -exec cp {} ./result/ \;
  ```
- **教训**：不要依赖固定目录名；`find` 比 glob 稳
- **证据**：`docs/execution/20261019-handoff-full.md`（输出目录一节）

### 坑 12：重复提交，白花钱

- **现象**：同一个任务出现两个号（`W202610180071475` / `W202610180071516`），因为「运行」按钮点了两次
- **正确做法**：提交后**先确认任务列表出现了新任务号**，再继续操作；重复的用 `POST /api/task/dcsTask/cancelTasks` 取消
- **教训**：UI 上点一次不等于提交一次，要看结果确认

### 坑 13：跨门 scVI 预估严重偏低（¥2.06 / 3h29m）

- **现象**：预估 0.2–0.5 元，实际 ¥2.06、跑了 3 小时 29 分
- **根因**：55,694 细胞 × 50 epoch，规模是门内的 12 倍，时间非线性
- **教训**：**scVI 的耗时随细胞数近似线性增长**，5 万细胞级别要有心理准备。这不是 bug，是规模问题
- **证据**：`docs/execution/20261019-handoff-full.md` §6.3

## 三、平台操作坑

### 坑 14：下载文件时加自定义头会 401

- **现象**：带 `X-Access-Token` 等头请求 `downloadFile` 返回 `401 令牌无效`
- **正确做法**：**只带 cookie**（`credentials: "include"`），其他什么都别加
  ```js
  fetch("/api/data/file/downloadFile?id=<fileId>&projectId=<pid>&zone=st",
        { credentials: "include" })
  ```
- **返回的是 gzip 原始字节**（魔数 `1f 8b 08 00`），二进制文件**不能用 `stringContent` 端点**（会 UTF-8 解码损坏）
- **证据**：`docs/execution/20261019-handoff-full.md` §7.5

### 坑 15：文件列表接口缺 `X-Client-App` 头会 400

- **现象**：`POST /api/data/file/meta/query` 返回 `{"code":400,"msg":"请求参数缺失：X-Client-App"}`
- **正确做法**：加 `X-Client-App: dcs-cloud-front`
  ```js
  fetch(`/api/data/file/meta/query?projectId=${pid}&parentId=${parent}&zone=st`, {
    method: 'POST', credentials: 'include',
    headers: { 'Content-Type': 'application/json', 'X-Client-App': 'dcs-cloud-front' },
    body: JSON.stringify({ projectId: pid, parentId: parent, zone: 'st', pageNo: 1, pageSize: 100 })
  })
  ```
- **注意**：`downloadFile` **不能**带这个头（带了反而 401），两个接口要求相反

### 坑 16：`/api/task/dcsTask/getUserTaskById` 同样要 `X-Client-App`

- **现象**：不带头返回 `{"code":400,"msg":"请求参数缺失：X-Client-App"}`
- **正确做法**：同上加头。**但**`/api/data/file/downloadFile` 不要加

### 坑 17：平台上传间歇失败（60030）

- **现象**：`POST /api/data/file/upload/local/other` 返回 `code 60030`「1个文件上传失败」
- **两个附加坑**：
  1. **`.whl` / `.bin` 等后缀会被内容检测拦截**，改名 `.txt` 上传，容器内去后缀恢复
  2. **报失败不等于没上去**（见坑 2）
- **绕行**：GenPilot 容器内 `dcs data push <本地路径> </Files/目标目录>`（不支持 `.py` 后缀，改 `.txt`）

### 坑 18：镜像管理入口「消失」

- **现象**：直接在 `#/project-management` 项目列表页，项目卡片菜单里**没有**「镜像管理」
- **正确做法**：**必须先进入项目内部**（点「数据管理」或任何子页面），左侧菜单才会出现完整列表，其中才有「镜像管理」
- **补充**：这个页面偶尔白屏（内容 iframe `display:none`、innerText 为空），刷新或从项目卡片重进可恢复

### 坑 19：文件选择器藏在嵌套 iframe 里

- **结构**：外层 `iframe[name^="Workflow__"]` 内还套着 `iframe[name="projectWorkflowV2Iframe"]`
- **正确做法**：同源可直接用 `outerIframe.contentDocument.querySelector('iframe[name=...]').contentDocument` 操作
- **注意**：勾选框列被 CSS 隐藏（`fixed--hidden`），点行没用，要**点 `td .text-over` 带 checkbox 的兄弟节点**或用坐标点

### 坑 20：WDL 编辑器 `fill()` 只追加不替换

- **现象**：编辑已有流程的脚本时，`fill()` 把新内容**加在原文后面**，导致脚本损坏
- **正确做法**：新建流程时编辑器为空，一次写入即可；改已有流程要**先全选删除**
- **证据**：`docs/execution/20261019-handoff-full.md`

### 坑 20b：下拉显示「无数据」≠ 后端没数据（2026-10-30 新增）

- **现象**：「个性分析 → 离线任务 → 计算资源」两个级联下拉点开都是「无数据」，`确定` 不可用，任务提交不了
- **第一反应（错的）**：项目没绑资源池 / 接口故障 / 容器没起
- **真实原因**：整页 reload 后抓 `performance.getEntriesByType('resource')`，该页在 `/stereonote/api/` 下**只发了 3 个请求**（`user/info`、`ipynb/getProjectInfoById`、`workspace/getlast`），**没有任何资源目录查询**。下拉从来没去后端取过数据
- **正确诊断法**：先看**请求有没有发**，再看返回。判断依据：
  ```js
  performance.getEntriesByType('resource')
    .map(r => r.name).filter(n => /stereonote\/api/.test(n))
  ```
  数一数里面有没有 `resource` / `remain` / `quota` 这类端点。没有 → 前端没发请求，别去查额度
- **为什么不绕**：`/stereonote/api/*` 需要 `X-Access-Token` 头，直接 fetch 一律 `{"code":401}`；而按项目纪律不读取、不复用凭据
- **绕法**：走 UI 之外的路 —— 需要人先在平台上把容器起起来，之后用 `dcs task run` 投递
- **教训**：「空列表」有三种成因（没请求 / 请求失败 / 返回空），**先分清是哪一种再动手**
- **证据**：`results/phase-20261030/image-build-evidence/offline-task-submit-blocked.json`

## 四、方法学与数字坑（会导致结论错）

### 坑 21：旧草表数字作废但仍在多处流传

- **现象**：网上/旧 PPT 里到处是 `80.9 / 38.3 / 40.5 / 22.4 / 11.9 / 79.5` 这组 oPCA 数字
- **真实情况**：**已作废**。两个原因：① 排除规则失效（`coarse_level=='unmapped'` 字符串过滤一个都没命中，74 个该排除的细胞留在分母）；② 评分器不是统一那版（v75c/v78b 容器输出，与冻结的 KNN/置换定义有实现差异）
- **冻结值 v98 口径**：`86.18 / 73.69 / 19.61 / 27.55 / 18.13 / 57.61`
- **⚠️ 2026-10-30 追补**：上面前四个数字里的鱼方向**是 v98 口径，已被 FIXKEY 取代**。v98 的斑马鱼方向同源映射没取反（已修 bug），FIXKEY 权威值为 `17.95 / 26.75 / 17.34 / 58.14`。人↔鼠两向两口径相同（`86.18 / 73.69`）。
- **所以真正的「正确数字」是 FIXKEY**：`86.18 / 73.69 / 17.95 / 26.75 / 17.34 / 58.14`
- **后果差别**：用旧草表是「4/6 个方向超过多数类基线」，用 v98 冻结值是「**3/6**」；用 FIXKEY 依旧是 3/6（差值 ≤1.4 个百分点，不翻转）
- **教训**：看到 80.9 那组立刻判定为旧草表；但**看到 19.61 那组要再判一次是不是 v98**
- **证据**：`docs/checkpoint-flash-20261002-evening.md` §4

### 坑 22：macro-F1 两个口径，差 0.05 就够翻转结论

- **现象**：同一份预测能算出两个 macro-F1
- **根因**：`truth-only`（只按真实标签集平均，平台 scVI 脚本默认） vs `union`（真实 ∪ 预测一起平均，多预测的类记 F1=0）
- **实例**：人→斑马鱼 coarse，truth-only 0.4516 / union 0.4014，**差 0.05**
- **正确做法**：跨方法比较**一律用 union**，从 18 份逐细胞预测独立重算
- **教训**：单独看 truth-only 不算错，但**不能和别的方法并列**

### 坑 23：把 `shuffle_p` 当成「优于多数类」的显著性

- **现象**：`shuffle_p = 0.04`，容易读成「这个方法显著更好」
- **真实含义**：它只回答「是否优于**随机打乱**」，**不回答「是否优于多数类基线」**
- **实例**：9 个斑马鱼方向的格子 acc < 多数类但 p≈0，属预期，不能写成「优于多数类」
- **证据**：`docs/checkpoint-flash-20261002-evening.md` §5.1

### 坑 24：`included` 旗标不等于分母

- **现象**：SAMap 的 per_cell 里 `included=1,398`，而 `n_q=1,505`，两个数不一样
- **根因**：`included` 用的是「truth ∈ 参考标签集」的新定义，**不参与 acc 计算**
- **后果**：误用 included 会得 `158/1398 = 0.113`，而正确值是 `0.1050`
- **教训**：引用时以后者（n_q/acc）为准

### 坑 25：批次指标的低值 ≠ 方法失败

- **现象**：三个方法 iLISI 都只有 1.006–1.120（满值 3），容易读成「都失败了」
- **真实含义**：同一份 scVI 潜空间上人→鼠 macro-F1 有 0.6683。潜空间把「细胞类型」和「物种」编码在近似正交的方向上
- **教训**：**两组证据必须一起报，只引一个就是误导**
- **证据**：`docs/reports/batch-mixing-and-crossphylum-feasibility-20261019.md` §7.2

### 坑 26：手写数字而不跑脚本

- **现象**：`report-03` 里六方向均值我按印象写成 `0.4988/0.4200/0.3922`，实际是 `0.4986/0.4611/0.3857`（SAMap 0.0334）
- **教训**：**所有表格数字必须从 `metrics.json` 用脚本生成**，或逐格核对。永远不要凭记忆写

## 五、工程协作坑

### 坑 27：中文引号与 Python 字符串冲突（两次）

- **现象**：生成组员文档的渲染脚本连续两次因引号转义失败，第二次还误把代码里的 `"宋体"` 改坏
- **正确做法**：**内容存 JSON，渲染脚本只读 JSON**。这样中文引号不会进入 Python 字符串字面量
- **落地**：`docs/reports/report02-walkthrough-content.json` + `scripts/build_report02_walkthrough.py`

### 坑 28：python-docx 设了列宽但 Word 不认

- **现象**：`cell.width = Cm(x)` 设完，渲染出来列宽全乱、内容挤成窄条
- **根因**：只设 cell 宽度不够，Word 需要同时有 `tblGrid` 列定义和 `tblLayout=fixed`
- **正确做法**：三样都要设
  ```python
  layout = OxmlElement("w:tblLayout"); layout.set(qn("w:type"), "fixed")
  tbl.tblPr.append(layout)
  grid = tbl.tblGrid
  for i, w in enumerate(widths):
      grid.gridCol_lst[i].set(qn("w:w"), str(int(w * 567)))   # 567 twip = 1cm
  for row in table.rows:
      for i, w in enumerate(widths):
          row.cells[i].width = Cm(w)
  ```

### 坑 29：Markdown → Word 渲染的四个小坑

- 三个连字符的分隔线渲染成字面文字（渲染器要显式处理成水平线）
- 由三个反引号包起来的代码围栏没被处理（要渲染成灰底等宽块）
- **列表项后面紧跟代码围栏**时，段落解析器会把围栏整段吞掉（循环的终止条件要把"这一行以三个反引号开头"也算进去）
- 表格单元格里"粗体套代码"（例如把 command 花括号形式写成加粗的代码片段）没解析干净，`add_rich` 要支持 bold 内嵌 code

### 坑 30：`bash -n` 的 exit code 被 Python 线程污染

- **现象**：`bash -n container/entrypoint.sh` 在 Python `subprocess.run(capture_output=True, text=True)` 里返回 1，但单独跑返回 0
- **根因**：文件里有中文，`text=True` 用 UTF-8 解码 stderr 时抛 `UnicodeDecodeError`，那个异常在线程里崩掉，`returncode` 就不可信了
- **正确做法**：检查 shell 语法直接跑 `bash -n`，别包在 Python 里；或加 `errors='replace'`

### 坑 31：容器 entrypoint 与脚本的环境变量契约不匹配

- **现象**：配方「看起来完整」，但从没真跑过
- **真实问题**：`entrypoint.sh` 只导出 `OPCA_ORTH_DIR`，但脚本 `ortholog_pca_dcs_v3_fixkey.py` 的 `ORTH_DIR` 变量**定义后再未使用**；脚本真正读的是 `OPCA_ORTH_MGI` / `OPCA_ORTH_HF` / `OPCA_ORTH_MF`，默认指向 `/Files/wheelhouse/`
- **后果**：容器里没有 `/Files`，**前置检查能过，脚本一 open 就 `FileNotFoundError`**
- **正确做法**：entrypoint 补齐三个变量。改完后用脚本静态比对「脚本读的 7 个变量 == entrypoint 导出的 7 个」
- **✅ 现状（2026-10-30 复核）**：已修。`container/entrypoint.sh` 现在同时导出 `OPCA_H5AD_DIR` / `OPCA_ORTH_DIR` / `OPCA_ORTH_MGI` / `OPCA_ORTH_HF` / `OPCA_ORTH_MF` / `OPCA_MAPPING` / `OPCA_OUT` 共 7 个，且第 39 行留了注释提醒
- **教训**：**「配方完整」和「跑得起来」是两件事**。没跑过的配方一定有坑
- **证据**：`container/README.md` §7.2

### 坑 32：Claude CLI 不可用

- **现象**：两次调用都返回 `unrecognized_model: deepseek-v4-pro[1m]`，并因超过 32000 输出 token 报错
- **教训**：这条路当时不通，别反复试

## 六、如果只记五条

1. **WDL 命令段用 `command <<< >>>`，不要用 `command { }`**（坑 1）
2. **Shell 变量一律加引号**，否则会 `cp -r /.` 拷根目录（坑 9）
3. **别人说「失败」要用独立证据复核**——文件可能已经上去了（坑 2）
4. **手写数字必错，一律跑脚本从 `metrics.json` 生成**（坑 26）
5. **没真跑过的配方一定有坑**，容器/流程要端到端验一遍（坑 31）
